# v1.6.0 业务模块扩展点

> 历史记录：本页保留原 v1.6.0 的发行事实。当前入口见 [v1.6.1 发布说明](/releases/v1-6-1)。

**v1.6.0 是 `mss-boot-sys/mss-boot-admin` 的业务模块扩展点发行版**，是 v1.5.0 之后的
向后兼容次版本：没有数据库结构迁移；新增的业务模块扩展点均为可选，未注册任何模块时
Admin 路由与行为不变。本页描述本次发行合同；是否已完成发布，以对应 Release、
包、镜像和公开网站的实际结果为准。

## 组件与产物

所有核心组件绑定同一经过本地完整验证的 merged `main` 提交。

| 发布面 | v1.6.0 身份与内容 |
| --- | --- |
| Root | `v1.6.0`；`mss`、`mss-mcp`、安装器、平台归档与校验和 |
| Framework | `mss-boot/v1.6.0`；协调版本，无源码变化 |
| Admin | `admin/v1.6.0`；`github.com/mss-boot-sys/mss-boot-admin/admin` |
| Admin Web | `web/antd-v6/v1.6.0`；前端归档与 `@mss-boot-sys/admin-web@1.6.0` |
| GitHub Packages | `npm.pkg.github.com`，npm 包唯一发布位置 |
| 后端镜像 | `ghcr.io/mss-boot-sys/mss-boot-admin:v1.6.0` |
| 前端镜像 | `ghcr.io/mss-boot-sys/mss-boot-admin-antd-v6:v1.6.0` |
| Docs | `docs/v1.6.0`；继续部署到 `https://docs.mss-boot-io.top` |

## 变更范围

- 业务 API surface（`business.Registration.Surfaces`）：核心强制的
  CORS → 认证 → `aud`/`iss` → CSRF → 模块中间件链；挂载任何 surface 即启用严格 Admin audience。
- Cookie 会话可选的双提交 CSRF（`SurfaceCSRF`，请求头名可配置，留空回落默认值）。
- `Runtime.Audit` 操作审计与核心脱敏。
- `Registration.Commands`：模块命令挂到宿主根命令。
- 前端 `defineBusinessAdmin({ extensions })` 扩展点。

完整条目见仓库 `CHANGELOG.md` 的 `[v1.6.0]` 节，以及
`docs/adr/2026-10-14-surface-security-chain.md`。

## 从 v1.5.0 升级

1. 备份代码、配置、数据库和当前可运行镜像，并安装 v1.6.0 工具，核对 `mss --version` 与
   `mss-mcp --version`；确认 `.mss/blueprint-manifest.json` 存在，保留旧基线以执行三方合并。
2. 按只读计划、应用、完整验证和最终空计划执行：

```shell
mss upgrade admin v1.6.0 --format json
mss upgrade admin v1.6.0 --apply --yes --format json
mss doctor --strict
mss verify --all
mss upgrade admin v1.6.0 --format json
```

最终计划必须无 create、update、delete 或 conflict。手工拼装或丢失 manifest 的项目应在新目录
生成 v1.6.0 基线，再迁入业务规格、配置与自有文件，不要伪造旧摘要或提交本地 `replace`。

3. 不注册业务模块时行为与 v1.5.0 一致。
4. 扩展页面与 Admin 同源、可读取 Admin 令牌；面向前台用户的页面应部署在独立域名。
5. 本地开发使用 Cookie surface 时，把 dev server 的 origin 加入 `business.SurfaceRegistration.CORS.AllowOrigins`。

无需数据库迁移。

## 发布与验证

源码变更通过 PR 合入 `main` 后冻结精确提交，执行完整本地验证，再按 Framework → Admin →
Admin Web → Root 顺序打标签，最后发布 `docs/v1.6.0` 并检查线上 `/release.json`。

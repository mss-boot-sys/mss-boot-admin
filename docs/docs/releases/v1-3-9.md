# v1.3.9 新仓库首发

**v1.3.9 是 `mss-boot-sys/mss-boot-admin` 的首次发行基线。** v1.3.8 及更早版本
已在原 `mss-boot-io` 组织发布；原组织不可见，不要求恢复历史流水线或补发历史产物。
历史页面和校验和保留原归属。本页描述本次发行合同；是否已完成发布，以对应 Release、
包、镜像和公开网站的实际结果为准，不以源码中的版本号代替发布证据。

## 组件与产物

所有核心组件绑定同一经过本地完整验证的 merged `main` 提交。正式提交由标签和 Release
记录，不在发布准备期间填入旧版本或分支提交。

| 发布面 | v1.3.9 身份与内容 |
| --- | --- |
| Root | `v1.3.9`；`mss`、`mss-mcp`、安装器、平台归档与校验和 |
| Framework | `mss-boot/v1.3.9`；`github.com/mss-boot-sys/mss-boot-admin/mss-boot` |
| Admin | `admin/v1.3.9`；`github.com/mss-boot-sys/mss-boot-admin/admin` |
| Admin Web | `web/antd-v6/v1.3.9`；前端归档与 `@mss-boot-sys/admin-web@1.3.9` |
| GitHub Packages | `npm.pkg.github.com`，本次 npm 包唯一发布位置 |
| 后端镜像 | `ghcr.io/mss-boot-sys/mss-boot-admin:v1.3.9` |
| 前端镜像 | `ghcr.io/mss-boot-sys/mss-boot-admin-antd-v6:v1.3.9` |
| Docs | `docs/v1.3.9`；继续部署到 `https://docs.mss-boot-io.top` |

生产部署固定 Release 中记录的镜像 digest 和下载校验和。

## 变更范围

- 将 Go 模块、源码导入、生成模板、前端包作用域、镜像与仓库链接迁至 `mss-boot-sys`。
- 将完整 Admin Web 包改为仅发布 GitHub Packages，生成项目与升级器支持对应认证和
  tarball integrity 校验。
- Go 工具链提升到 **1.27.2**，前端使用 Node 24、pnpm 10.34.5；同步 Framework、
  Admin、前端、Docs 和生成项目依赖基线。
- 授权依赖迁至 **Casbin v3.11.0**。引用 Casbin 导出类型的业务代码需要适配，不能将
  本次命名空间和依赖迁移视为无代码改动的补丁升级。
- 纳入 OIDC 管理能力、编译期工作台/头像/布局扩展、生成器及安装升级修复；具体接口和
  权限仍以代码、迁移和能力合同为准。
- 发布改为本地完整验证后创建组件标签，流水线负责构建、打包和发布，不再要求托管候选
  预览、npmjs Trusted Publisher 或单独稳定晋升轮次。

测试证据报告同时脱敏原始路径和正则转义后的路径，避免带点号、括号等字符的工作目录出现在导出报告中。

## 首次安装与认证

从[快速开始](/getting-started)选择平台安装器，再核对工具版本：

```shell
mss --version
mss-mcp --version
```

前端安装、生成与升级需要 GitHub Packages 的包读取认证，配置见
[包与导入边界](/getting-started/packages)。`.npmrc` 只包含 scope 和
`${NODE_AUTH_TOKEN}` 引用，不包含真实秘密。

首次初始化通过隐藏输入或一次性 `MSS_ADMIN_INITIAL_PASSWORD` 设置密码；没有默认密码。
本地前端为 `http://127.0.0.1:8001`，初始账号为 `admin`。

## 从旧组织版本迁移

1. 备份代码、配置、数据库、业务数据和现有可运行镜像；原组织不可见，因此回滚前必须
   验证自己留存的旧制品可用，不能假定旧远端可重新下载。
2. 安装 v1.3.9 工具并检查 `.mss/blueprint-manifest.json`，保留旧基线以执行三方合并。
3. 更新业务自有 Go imports 到 `github.com/mss-boot-sys/mss-boot-admin`；替换旧 npm
   scope，配置 GitHub Packages 读取权限；检查 CI、Docker 构建和私有镜像拉取凭据。
4. 引用 Casbin 类型的扩展更新为 `github.com/casbin/casbin/v3`，编译并验证允许与拒绝
   两类权限路径。策略存储规则没有因此自动改变。
5. 按只读计划、应用、完整验证和最终空计划执行：

```shell
mss upgrade admin v1.3.9 --format json
mss upgrade admin v1.3.9 --apply --yes --format json
mss doctor --strict
mss verify --all
mss upgrade admin v1.3.9 --format json
```

最终计划必须无 create、update、delete 或 conflict；业务自有和未知文件应保留。手工拼装
或丢失 manifest 的项目在新目录生成 v1.3.9 基线，再迁入业务规格、配置与自有文件，不要
伪造旧摘要或提交本地 `replace`。

数据库升级先在备份副本演练，运行 `migrate`、一次 `server -a` 同步 API 权限，再启动
长期服务。OIDC 表与相关权限按当前迁移增量创建，复查登录、SSO、租户隔离和角色授权。
回滚恢复成套旧应用、配置和必要的数据备份，禁止为回退执行未经验证的破坏性删表。

## 发布与验证

源码、文档与流水线变更必须通过 PR 合入 `main`，再冻结远端 `main` 已包含的精确提交。
在该干净提交执行完整本地验证，包含各 Go 模块、前端、生成器、外部 Thin Host、安装和
重复升级、数据库新建与升级、镜像交付及内置浏览器验收。

标签按 Framework → Admin → Admin Web → Root 顺序发布。Admin 发布时解析公开的
精确 Framework 版本；其余流水线只进行必要来源校验、构建和产物发布。核验二进制版本、
校验和、GitHub Packages tarball、镜像与 Release 来源一致。

最后发布 `docs/v1.3.9`，检查线上 `/release.json` 的版本和完整提交，并在内置浏览器刷新
首页、本页及嵌套路由，确认内容、控制台和网络请求。Docs 失败只修复网站，不重写已发布
核心标签；本次任务在 Docs 部署核验完成后交付。
